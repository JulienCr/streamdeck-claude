## 1. Session status and `claude agents --json`

During a normal permission prompt the interactive session reads:

```json
{"pid":2127664,"kind":"interactive","name":"spike-cc-c1","status":"waiting","waitingFor":"permission prompt"}
```

Busy → `"busy"`, idle → `"idle"` (no `waitingFor` key). `--all` only adds finished
background entries. Background entries carry `state` (`blocked`/`failed`/`done`) and
`id`, no `pid`.

`~/.claude/sessions/<pid>.json` carries the same `status`/`waitingFor` plus
`statusUpdatedAt`, `tmux`, `version`. Transition trace (file polled every 0.5 s,
prompt answered at 304.6):

```
304.591 {"status":"waiting","waitingFor":"permission prompt"}
305.107 {"status":"busy","waitingFor":null}
308.713 {"status":"idle","waitingFor":null}
```

Today `src/sessions.ts` coerces anything but `busy` to `idle`, and reads
`waitingFor` for background sessions only. The event log already gives
`awaiting*` priority over `busy` (`deriveState`), so #8's suspected bug does not
reproduce; `waitingFor` is a free second opinion for interactive sessions.

Spawn cost (ms, from Windows):

| Command | min | median | max |
|---|---|---|---|
| `claude.exe agents --json` (native) | 269 | 285 | 460 |
| `wsl.exe -d Ubuntu -- ~/.local/bin/claude agents --json` | 751 | 834 | 1640 |
| same through `bash -lc` | 1509 | 1689 | 1793 |
| `wsl.exe -- bash -c 'kill -0 1'` (current WSL liveness) | 147 | 175 | 231 |
| `tasklist.exe /NH /FO CSV` (current Windows liveness) | 2323 | 2441 | 3663 |

From WSL itself, `claude agents --json` takes 0.54–0.69 s. The surprise is
`tasklist.exe`: 2.4 s per call is the slowest thing in the tick today — worth its
own look independently of #36.

## 2. Blocking `PermissionRequest` hook

- **Display:** the terminal shows the full permission dialog immediately, while the
  hook runs. Answering it in the terminal resolves the request; the hook keeps
  running to completion and its late output is ignored. Session file reads
  `status: waiting` throughout.
- **Timeout:** with `"timeout": 5` and a 10 s sleep, the hook got SIGTERM at exactly
  5 s, no visible error, prompt unchanged. Docs: 600 s default for command hooks, no
  stated maximum; `async` hooks are not subject to it.
- **Outputs, all verified:**
  - `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`
    → runs, pane says "Allowed by PermissionRequest hook".
  - `deny` + `message` → not run, the reason is shown and relayed by the model.
  - `allow` + `updatedPermissions` = the payload's suggestions → applied live
    (`setMode acceptEdits` switched the footer). An `addRules` entry with
    `destination: "localSettings"` wrote `<project>/.claude/settings.local.json`
    and the next matching command ran with no prompt.
- **Payload** (no `tool_use_id`, unlike `PreToolUse`):

```json
{
  "session_id": "2f1c0157-…", "cwd": "…", "prompt_id": "b4247a37-…",
  "permission_mode": "default", "hook_event_name": "PermissionRequest",
  "tool_name": "Bash",
  "tool_input": {"command": "touch q2a.txt", "description": "Create empty file q2a.txt"},
  "permission_suggestions": [
    {"type": "addDirectories", "directories": ["…/spike-cc"], "destination": "session"},
    {"type": "setMode", "mode": "acceptEdits", "destination": "session"}
  ]
}
```

  For a non-file command (`chmod 700 q2d`) the suggestion is a rule instead:
  `{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"chmod 700 q2d"}],"behavior":"allow","destination":"localSettings"}`.
  The array's content depends on the command — "Always" must echo whatever came in,
  not build its own rule.

Not tested: two `PermissionRequest` hooks racing; a hook that returns a decision
*after* the user already answered in the terminal.

## 3. `AskUserQuestion` through `PreToolUse`

Hook on matcher `AskUserQuestion`, returning the original `questions` plus `answers`
keyed by question text:

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow",
 "updatedInput":{"questions":[{"question":"Pick a fruit","header":"Fruit","options":[{"label":"Apple","description":"Choose Apple"},{"label":"Banana","description":"Choose Banana"}],"multiSelect":false}],
 "answers":{"Pick a fruit":"INJECTED_ANSWER_ZEBRA"}}}}
```

The model received the injected string; the pane only showed
`Answered Claude's questions: · Pick a fruit → INJECTED_ANSWER_ZEBRA`. A string that
is not an option label was accepted (docs: labels, comma-joined for multi-select).
The incoming `tool_input` is exactly the `questions` array above, with `tool_use_id`.

## 4. Hook cost and `async: true`

`notification.ps1` per call, from Windows (ms):

| Variant | min | median | max |
|---|---|---|---|
| `powershell.exe -File //wsl.localhost/…` (installed today) | 373 | 464 | 959 |
| `powershell.exe -File` local copy | 341 | 358 | 925 |
| `pwsh.exe` over UNC | 314 | 340 | 704 |
| `pwsh.exe` local copy | 310 | 324 | 408 |
| baseline `powershell.exe -NoProfile -Command exit` | 294 | 343 | 363 |
| baseline `pwsh.exe -NoProfile -Command exit` | 267 | 288 | 305 |

Startup dominates; UNC adds ~100 ms, the script itself 15–120 ms. The plugin cache
(#32) removes the UNC hop; only `async: true` removes the rest from the tool path.
`notification.sh` on WSL: 136 ms median (132–161), almost all of it the ~10 `jq`
spawns + `perl`.

Order with `async: true` (hook sleeping a random 0–300 ms before appending,
`PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit`):

- 5 sequential tool calls: file order = real order, async and sync alike.
- 6 parallel tool calls: Pre events interleave out of launch order in **both** modes;
  all Pre still precede all Post, `Stop` last.
- Payloads carry no sequence number. The smallest sequential gap seen was ~340 ms,
  so an async inversion stays possible in theory for events closer than the hook's
  own run time; none was observed.
